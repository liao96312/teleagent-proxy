# 封号机理与规避（含真实案例）

> 本文档基于一次**真实封号事件**的取证。请务必阅读。

## 1. 结论先行

- TeleAgent 网关有**服务端风控**。反代属于「App 外使用」，**有被封的真实风险**。
- 封禁是**账号级**的：一旦被封，**官方 App 也一起用不了**（不只是反代）。
- 错误码链：`40105 疑似攻击` → `40109 current user is banned`。
- **没有 100% 规避办法**。想零风险 = 只用官方 App。

## 2. 真实案例时间线

账号：`v1_public_2082348480363835392`（tenant `Em9xR4`）

| 时间 | 事件 | 证据 |
|---|---|---|
| 09-11 白天 | 逆向期间对网关发送**大量错误签名**请求（试错） | 触发 `40105 疑似攻击` |
| 09-11 16:06:12 | App 内置 server 首次记录 `40109 current user is banned` | `super-agent-server-2026-09-11.log` |
| 09-11 16:00 前后 | App 出现 **`GET /app status=401` 风暴**（客户端反复重试鉴权失败） | 同上 |
| 09-11 全天 | App 侧 LLM 调用 **1612 次**（历史最高，日志 24MB / 155955 行） | 日志统计 |
| 09-12 08:55:58 | 再次 `40109`（App 前端 `[EventStream] Session error: current user is banned`） | `js-2.5.0.log` |
| 09-12 当天 | 反代同样返回 `{"code":40109,"message":"current user is banned"}` | shim 实测 |
| — | **令牌本身未过期**（JWT `exp` 还剩 73.7h） | 解 JWT 得 |

> 关键点：**封禁不是 token 失效**，而是服务端把账号拉黑；App 与反代**同时**失效。

## 3. 触发因素（按可能性排序）

1. **错误签名的爆破/试探（主因）**
   逆向时为猜算法发了大量非法请求。`40105 疑似攻击` 是风控最典型的判定。
   即使之后算对了，风控分已经被打上，**封禁是延后生效的**。
   👉 **绝对不要对生产网关做签名爆破。**

2. **"第二客户端"流量特征（方案 A 固有问题）**
   shim 的请求不是 App 发的：没有 App 的心跳、没有浏览器/渲染进程指纹、请求节奏不同，
   服务端能看出「同一账号、两种客户端」。

3. **用量过大**
   封号当天 App 侧 1612 次 LLM 调用（历史峰值），叠加前两条更容易触发。

4. **并发/竞态**
   反代与 App 同时占用同一账号、或短时间并发大量请求。

## 4. 规避建议（降低概率，非保证）

| 措施 | 说明 | 效果 |
|---|---|---|
| **不做签名爆破** | 一次性把算法搞对，别试探 | ★★★★★ |
| **走方案 B（App 本地 server）** | 出站由 App 进程发出，指纹一致 | ★★★★★ |
| 不做并发、限速到"人类节奏" | 加抖动 sleep、串行化 | ★★★★ |
| 单一设备身份 | 固定 `deviceId`/`installId`，不要忽变 | ★★★ |
| 严格对齐 App 请求头 | OS/版本/UA/客户端类型等 | ★★★ |
| 控制日用量 | 别当 7×24 压测机用 | ★★★ |
| 用**独立的小号**做实验 | 别拿主号练手 | ★★★★ |

## 5. 已经被封了怎么办

1. **立刻停手**：停止一切反代流量（含关闭 shim）。反复重试只会更糟。
2. **等待**：此类封禁多为**临时**（常见 24h～7d）。到期后先用官方 App 验证是否解封。
3. **申诉**：联系 TeleAgent 客服。⚠️ 若被判定为 out-of-app 使用，申诉**可能反噬**（等于自认），自行权衡。
4. **换号**：需要新的手机号重新注册。
5. **接受结论**：反代方案对**这个账号**已不可用。

## 6. 给使用者的忠告

本项目只应作为**逆向/协议研究**用途，在**自己的机器、自己的账号**上小量验证。
把它当成日常主力模型通道去刷量，被封是概率问题，不是会不会的问题。
