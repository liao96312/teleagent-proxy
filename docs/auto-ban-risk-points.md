# 自动化封禁：风险点清单

> 基于两次真实封禁 + App 导出日志 + 内核二进制。目标是列出**可能被自动化规则命中**的地方。

## 0. 先明确：封禁是自动化的，而且有"计数"

历史封禁通知原文（从**内容审核接口**返回，被 App 记为 `Moderation rejected raw content`）：

```
尊敬的用户，您好：
系统监测到您疑似【多次尝试违规操作】，现已暂停您的使用权限。
如对处理结果有异议，欢迎联系客服进行核实解决。
预计自动解封时间：2026-08-28 09:54:36。
```

三个要点：
1. **「多次尝试」** → 是**累计计数**，不是单次判定
2. 通知由**审核接口**返回 → **审核链路就是封禁的执行点**
3. 有**自动解封时间** → 限时封禁，不是永久

## A. 已证实的自动封禁触发

| # | 触发 | 证据 | 我们踩过吗 |
|---|---|---|---|
| A1 | **签名校验失败累计**（40104/40105） | 账号 1 被封；40105 的文案就是"疑似攻击" | ✅ 踩过（爆破） |
| A2 | **内容审核被拒后继续尝试** | 日志里同一段内容 `rejected ×55` + `blocked ×54`，间隔几秒 | 不是我们 |

> A1/A2 的共同点：**失败/拒绝后的重复尝试**被计数。这就是"多次尝试"的含义。

## B. 平台结构上能自动检测的（未证实，但机制上成立）

| # | 风险点 | 为什么能被检测 | 我们的状态 |
|---|---|---|---|
| B1 | **LLM 调用没有对应的内容审核记录** | 审核是**每条消息**都做的（`chat_user_message` + `chat_assistant_output`），审核接口是封禁执行点；我们直连完全没有审核 | 🔴 **存在** |
| B2 | **工具调用没有对应的 `security/instruction/review`** | 内核对每个工具调用先 review 再执行，共用同一 `X-Request-Id` | 🟡 已停用工具 → 不触发 |
| B3 | **模型消耗 = 0 的工具调用** | 正常生图必然在某个模型轮次内 | 🟡 同上 |
| B4 | **`X-Message-Id` 在会话里不存在** | 内核用真实 messageID；我们随机编 | 🔴 存在（每个请求） |
| B5 | **`X-Session-Id` 不存在 / 没有标题** | 真会话有小模型生成的标题记录 | 🟠 已改为建真会话+生成标题 |
| B6 | **设备指纹被多账号共用** | deviceId/installId 每请求都带 | ✅ 已可随机化 |
| B7 | **同一 token 突然换设备指纹** | 平台看到"账号 X 先用设备 A，后用设备 B" | ⚠️ **换指纹时必须伴随重新登录**，否则像盗号 |
| B8 | **body 语义**（tools / system prompt 与内核不同） | 内核发固定的 tools 集 + 专属 system prompt | 🔴 存在 |
| B8' | **同版本内正版提示词是固定文本**（29k 里无机器名/账号/路径；grep 已验证）→ 按内容指纹比对技术上可行 | 见 `docs/pi-subagent.md` §8.7；但 `instructions` 的 4 个 memory 文件是用户可写的，若真进系统提示词则全文比对不可能（**待验证**） | ⚠️ 自己引入：`TA_AGENT_MODE=replace` 时暴露最大 |
| B9 | **会话创建频率异常** | 正常用户不会几分钟建 10+ 个会话 | 🟠 测试时踩过 |
| B10 | **并发 / 频率 / 24h 匀速** | 脚本特征 | 🟠 需自律 |
| B11 | **传输层指纹**（TLS/UA/头序） | Go vs Node 的 ClientHello 不同 | ✅ 已用同版本 Go 修 |
| B12 | **活跃会话数超限** | 日志里有 `send_active_session_limit_check` | 🟡 未知阈值 |
| B13 | **多 IP / 代理漂移** | 换网络、挂代理 | 🟠 需注意 |
| B14 | **客户端版本过低** | 40301 | 🟢 用 2.5.0 |

## C. 结论：我们的风险排序

| 优先级 | 风险 | 现状 | 能做吗 |
|---|---|---|---|
| 🔴 1 | **B1 无内容审核记录** | 每条消息都缺 | 要补就得复刻审核接口（需密钥+协议） |
| 🔴 2 | **B4 `X-Message-Id` 编造** | 每个请求 | 可用真会话的消息 ID（要先建消息） |
| 🔴 3 | **B8 body 语义** | 方案 A 一直存在 | 只能改走方案 B |
| 🔴 3' | **B8 被自己搬进方案 B**（改内核 agent 的 system prompt） | `TA_AGENT_MODE=append`（默认）保留正版全文只追加；`replace` 则替换 | 默认 append；主号别用 replace；最保守用 `TA_AGENT=""` 退回 v2 |
| 🟠 4 | **B7 换指纹不换登录** | 本次已随重登一起做，**算安全的** | 以后务必"换指纹 + 重新登录"成对做 |
| 🟠 5 | B9/B10/B13 行为面 | 靠自律 | 限速、别并发、别乱换网络 |
| 🟡 6 | B2/B3 工具类 | 已停用 | 保持停用 |

## D. 换指纹的正确姿势（重要，容易踩）

**错误做法**（= 高风险）：
```
登录着账号 A → 直接改 device-meta.json → 不重新登录，继续用
→ 平台看到: 同一个 token 从新设备发请求 = 盗号 / 共享账号特征
```

**正确做法**：
```
1. 退出登录（或直接杀 App）
2. 换指纹: python scripts\randomize-fingerprint.py
3. 重启 App → 重新登录（此时 App 会因 fingerprint/generation 变化要求重登，正好）
4. 重启 shim
```

> 本次操作正好符合"正确做法"：换指纹时 App 因 install generation 变化清掉了登录 cookie，
> 所以会以新设备身份重新登录 —— **这次是安全的**。

## E. 还没弄清、值得继续观察的

1. **内容审核接口的地址与协议**（要补 B1 就得逆它）
2. **审核拒绝的计数阈值**（几次算"多次"）
3. **`send_active_session_limit_check` 的具体阈值**
4. **平台是否真的按 `X-Request-Id` 关联 review/审核与执行请求**（这是 B1/B2 成立的前提）
5. **B8 的判定方式**（是否真做 body 语义比对）—— 更具体地：**系统提示词里那 4 个 memory 文件
   是否真的被追加进发往网关的 body**（验证方法见 `docs/pi-subagent.md` §8.7，需要 App 在跑 +
   `scripts/scan-gateway-req.py` dump wire）。这一条决定了“改系统提示词”是 🔴 还是可接受
